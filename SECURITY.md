# Security

This document describes how the Caldim Engineering site is protected, so that
whoever operates it knows what is guarding what — and, just as importantly,
what is *not* covered and still needs a decision from you.

---

## Reporting a vulnerability

Email **estimator@caldimengg.in** with the words *security report* in the
subject. Please include enough detail to reproduce the issue. Don't open a
public issue for anything exploitable.

---

## The short version

| Area | What protects it |
|---|---|
| Passwords | argon2id (19 MiB, t=2, p=1), per-user salt, never stored or logged in any recoverable form |
| Second factor | TOTP (RFC 6238), secrets AES-256-GCM encrypted at rest, 10 single-use recovery codes |
| Sessions | Opaque 256-bit tokens; only their SHA-256 digest is stored; `__Host-` prefixed, `HttpOnly`, `Secure`, `SameSite=Lax` |
| CSRF | Origin + `Sec-Fetch-Site` check, plus a `__Host-` prefixed double-submit token |
| Brute force | Per-IP and per-account rate limits, plus account lockout after repeated failures |
| Input | Every request body parsed by a Zod schema before anything reads it |
| Uploads | Magic-byte sniffing, dimension caps, and a full re-encode that strips EXIF and any embedded payload |
| Output | Strict CSP with a per-request nonce; no `unsafe-inline` for scripts |
| Auditing | Append-only log of every privileged action, successful and failed |

## Authentication

### Passwords

Hashed with **argon2id** at OWASP's recommended second profile: 19 MiB of
memory, two iterations, one lane. Memory-hardness is the point — it means an
attacker holding a stolen hash pays RAM for every guess, rather than getting
the near-free parallelism a GPU has against bcrypt or a bare SHA.

The policy is length-first, following NIST SP 800-63B: a minimum of 12
characters, a small blocklist of common choices, and a check that the password
doesn't contain the user's own name or email. There is deliberately no
"one uppercase, one symbol" rule, because those push people toward `Passw0rd!`
and away from the long passphrases that actually resist cracking.

### Account enumeration

A wrong password and an account that doesn't exist return **the same message,
the same status code, and take the same amount of time**. When the email is
unknown, the server still performs a full argon2 verification against a dummy
digest, so a missing account can't be identified by a fast rejection.

### Lockout and rate limiting

Two independent budgets apply to every sign-in attempt — one keyed on the
client IP, one on the account. Neither a single noisy address nor a
distributed attempt against one account slips through the gap the other would
leave. Counters live in the database, not process memory, so restarting the
server does not hand an attacker a fresh budget.

After `MAX_LOGIN_ATTEMPTS` consecutive failures (default 5), the account locks
for `LOCKOUT_MINUTES` (default 15).

### Two-factor authentication

TOTP, compatible with any authenticator app. Deliberately not SMS, which is
the weakest second factor in common use.

- The secret is generated server-side and stored **AES-256-GCM encrypted**,
  keyed by `APP_ENCRYPTION_KEY`. A database dump alone does not yield working
  secrets.
- Enrolment stores the candidate secret with `totpEnabled` still false. Nothing
  takes effect until a code generated by the user's own device proves the
  secret arrived intact — so an abandoned enrolment can never lock anyone out.
- Ten recovery codes are issued once, at enrolment. Only their argon2id hashes
  are kept. Each works once; redeeming one also revokes every other session,
  on the assumption that a recovery code means a device has been lost.
- Turning 2FA **off** requires re-entering the password. Removing a security
  control is exactly the moment to re-check identity.

Set `REQUIRE_TOTP=true` to force every admin to enrol before they can reach
anything else.

## Sessions

The cookie carries an opaque random token and nothing else — no user id, no
role, no signed claims. Authority lives in the database row, so revoking a
session takes effect on the very next request rather than waiting for a token
to expire.

- Only the **SHA-256 digest** of the token is stored. A database leak cannot be
  replayed as a live session.
- **`__Host-` prefix** (in production). Browsers enforce this: the cookie must
  be `Secure`, `Path=/`, and carry no `Domain` attribute — which makes it
  impossible for a sibling subdomain to overwrite it.
- **`HttpOnly`** — unreachable from JavaScript, so an XSS foothold cannot steal it.
- **`SameSite=Lax`** — not sent on cross-site form posts.
- **Two timeouts**: an idle timeout (default 60 minutes, refreshed by activity)
  and an absolute timeout (default 12 hours, never extended). A session left
  open on a shared machine dies on its own.
- A **new session id is always minted at sign-in**, never reused from a
  pre-login cookie. That is what closes off session fixation.
- Changing the password **revokes every other session** automatically. So does
  redeeming a recovery code.

## CSRF

Two independent layers:

1. **Origin check.** `Sec-Fetch-Site` must be `same-origin` or `none`, and any
   `Origin` header must match the configured site URL or the request `Host`.
   A request carrying neither header is refused outright.
2. **Double-submit token.** The request must echo, in the `x-caldim-csrf`
   header, the value held in a cookie. An attacker on another origin can cause
   a request to be *sent* with our cookies, but the same-origin policy stops
   them reading the cookie, so they cannot know what to echo back.

The CSRF cookie carries no HMAC, and doesn't need one. The classic weakness of
double-submit is a sibling subdomain writing cookies for the parent domain, and
the `__Host-` prefix closes that off at the browser level — a stronger
guarantee than a signature, with no secret to share between the Edge runtime
that mints the token and the Node runtime that checks it.

The token is minted in **middleware**, because a Server Component cannot write
cookies. Route handlers refuse any mutating request that fails either layer.

## Input validation

Every request body is parsed by a **Zod schema** before anything else reads it.
Parsing, not checking — the rest of the application only ever sees typed,
bounded, trimmed data, and it is the *parsed output* that gets stored, so extra
fields a client sent are dropped rather than persisted.

Notable specifics:

- **Content keys are allowlisted.** The content API can only write the eleven
  rows the site knows how to render; it is not a general-purpose "write
  anything into the database" endpoint.
- **URLs are restricted to `http(s)`.** Without this, a `javascript:` URL saved
  into a leader's LinkedIn field would become stored XSS the moment it was
  rendered as an `href`.
- **Control characters are stripped** and Unicode is NFKC-normalised on every
  text field.
- **Stored content is re-validated on read**, not only on write. A row edited
  directly in the database, or written by an older schema, cannot inject an
  unexpected shape into a component — it falls back to the shipped default and
  logs a warning.

SQL injection is not a concern here: every query goes through Drizzle's
parameterised query builder. No string concatenation touches SQL.

## File uploads

The rule is that nothing the browser sends is trusted — not the filename, not
the declared `Content-Type`, not the extension.

1. **Size is checked twice**: the declared `Content-Length` before buffering,
   and the actual byte length after reading.
2. **Type is sniffed from magic bytes**, ignoring what the client claimed. Only
   JPEG, PNG, WebP and AVIF are accepted for images.
3. **Dimensions are capped** at 40 megapixels, which stops a decompression
   bomb — a file that is tiny on disk and enormous once decoded.
4. **The image is fully re-encoded** to WebP through sharp. This is the
   decisive step: a polyglot file (a valid PNG with a script appended after the
   image data) does not survive, because only the decoded pixels carry across.
   EXIF goes with it, which also strips the GPS coordinates phones embed in
   photographs.
5. **Identifiers are generated server-side.** The user-supplied name is kept
   only as a display label; the Cloudinary `public_id` is a random token.
6. **Nothing is written to our filesystem, and nothing is served from our
   origin.** Assets go to Cloudinary and are delivered from `res.cloudinary.com`
   — a different origin, so even a hostile file has no same-origin context to
   run in.

Together, that leaves the classic "upload a file, then get the server to
execute it" chain with no link to grab onto.

Note the ordering: the re-encode happens **before** the upload, not on the way
out. What Cloudinary stores is already clean, rather than being sanitised only
when a transformation is requested.

### Video

Video is too large to buffer through a route handler, so the bytes go from the
browser straight to Cloudinary. That would normally mean trusting the client,
so the flow is split in two and the client is trusted at neither end:

1. The browser sends the file's **first 32 bytes** and its size. The server
   identifies the container from the magic bytes (ISO base media for MP4/MOV,
   EBML for WebM/MKV), enforces the size ceiling, and only then issues a
   signature.
2. The signature **covers the folder and `public_id` the server chose**, so the
   browser cannot upload elsewhere, overwrite an existing asset, or change the
   resource type. It expires with Cloudinary's one-hour timestamp window.
3. On completion the server **asks Cloudinary what actually landed** and records
   that. The client's account of its own upload is never the source of truth —
   otherwise anyone holding a session could register an arbitrary `public_id`
   and have the site render an asset they do not own. An asset outside the
   signed folder is rejected outright; one over the size ceiling is deleted.

The Cloudinary API secret is read from the server environment only. It signs
uploads and deletes, and never reaches a client bundle or a response body.

RFQ attachments (PDF, ZIP, DWG, DXF, IFC) are stored as Cloudinary `raw`
resources — delivered as an opaque download rather than interpreted as media —
and the public `/api/media/[id]` route **refuses to resolve `raw` rows at all**,
so an attachment is reachable from the admin area only.

## Security headers

Set on every response by `middleware.ts`:

- **`Content-Security-Policy`** with a per-request nonce and `strict-dynamic`.
  No `unsafe-inline` for scripts. `object-src 'none'`, `base-uri 'none'`,
  `frame-ancestors 'none'`, `form-action 'self'`.
  `style-src` keeps `'unsafe-inline'` — React writes inline style attributes
  for every animated transform and there is no nonce mechanism for attribute
  styles. It cannot be used to execute script.
- **`Strict-Transport-Security`** — two years, `includeSubDomains`, `preload`.
- **`X-Content-Type-Options: nosniff`**
- **`X-Frame-Options: DENY`** (belt and braces with `frame-ancestors`)
- **`Referrer-Policy: strict-origin-when-cross-origin`**
- **`Cross-Origin-Opener-Policy`** and **`Cross-Origin-Resource-Policy`**: `same-origin`
- **`Permissions-Policy`** switching off camera, microphone, geolocation,
  payment, USB and the rest — so a future dependency can't quietly start
  asking for them.
- `X-Powered-By` is suppressed, and the admin area is served `no-store`.

**Fonts are self-hosted.** There is no request to `fonts.googleapis.com`, which
means `font-src 'self'`, one fewer third party in the critical path, and no
request that leaks a visitor's IP address to another company.

### The Cloudinary exceptions

Adding a media host means the CSP can no longer be `'self'` throughout. Three
directives are widened, and the two Cloudinary hosts are kept deliberately
apart:

| Directive | Added | Why |
|---|---|---|
| `img-src` | `https://res.cloudinary.com` | Uploaded photos and video poster frames are delivered from there. |
| `media-src` | `https://res.cloudinary.com`, `blob:` | Video playback. |
| `connect-src` | `https://api.cloudinary.com` | The signed direct video upload — the only cross-origin request the app makes. |

`res.cloudinary.com` only ever *serves* bytes, so it is trusted to supply media
and nothing else. `api.cloudinary.com` *accepts* uploads, so it appears in
`connect-src` alone — a page can POST a video to it, but a response from it can
never become an image, a script or a stylesheet.

Neither host appears in `default-src`, `script-src` or `frame-src`. Cloudinary
cannot execute code on this origin; it can only be read from and written to, in
those three specific ways.

Next's image optimiser is pinned the same way. Its `remotePatterns` entry
restricts the pathname to `/${CLOUDINARY_CLOUD_NAME}/**` rather than allowing
the whole host — the optimiser is a fetching proxy, and a bare hostname would
let it pull images from any Cloudinary account on the internet.

## Auditing

Every privileged action — successful *and* failed — is written to an
append-only log: who, what, when, and a salted hash of where from. Failures
matter as much as successes; a run of `login.failure` rows is the earliest
signal anyone gets that the site is under attack.

- **IP addresses are stored as salted HMACs**, never in the clear. The log
  stays useful for spotting a pattern without holding personal data.
- **Metadata is redacted by key.** Anything whose key matches
  `pass|secret|token|code|hash|otp|key|cookie` is replaced with `[redacted]`
  before it is written, whatever the caller passed.
- The log is visible at `/admin/activity`, and recent failures are surfaced on
  the dashboard.

## Operational notes

### Secrets

`SESSION_SECRET`, `APP_ENCRYPTION_KEY` and `IP_HASH_SALT` are **required in
production**. The application refuses to boot if any is missing, shorter than
32 bytes, or left at a placeholder value — turning "we forgot to set the
session secret" from a silent hole into a boot failure.

Generate each one separately:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
```

Rotating `APP_ENCRYPTION_KEY` invalidates every stored TOTP secret; users will
need to re-enrol. Rotating `SESSION_SECRET` is harmless — sessions are opaque
tokens, not signed data.

### First run

`npm run db:seed` creates the owner account and prints a generated password
**once**. It is not written to disk in readable form, and the account is
flagged `mustChangePassword`, so it cannot survive first sign-in.

### Account recovery

There is deliberately **no "forgot password" endpoint**. If 2FA is lost and the
recovery codes are gone, recovery requires shell access to the machine holding
the database:

```bash
npm run admin:reset -- admin@caldimengg.com --clear-2fa
```

That is the point: recovery is gated on physical/SSH access to the server, not
on control of an inbox, so there is nothing on the public site for an attacker
to work against.

### Backups

The database is Supabase Postgres. Treat any dump as sensitive — it contains
password hashes and encrypted TOTP secrets:

```bash
pg_dump "$DIRECT_DATABASE_URL" --no-owner --format=custom -f backup/caldim-$(date +%F).dump
```

Media lives in Cloudinary and is backed up there, separately. The two are not
consistent with one another: restoring an old database alongside current media
leaves rows pointing at assets that may since have been deleted.

### Database access

The app connects with a Postgres role over a pooled connection, so **Row Level
Security is not the access-control boundary** — the session, CSRF and rate-limit
guards in `lib/security` are. Do not expose the Supabase anon or service keys to
the browser, and do not add client-side Supabase queries expecting RLS to cover
them; this application does not use it.

Rotate the database password and the Cloudinary API secret if either is ever
committed, pasted into a ticket, or shared outside the team.

## What is *not* covered

Being explicit about the gaps is more useful than implying there aren't any.

- **TLS terminates upstream.** This application assumes it sits behind a
  reverse proxy or platform that handles HTTPS. `SECURE_COOKIES` must stay true
  in production; setting it false disables the `__Host-` prefix and the
  `Secure` flag on both cookies.
- **`X-Forwarded-For` is trusted for the first hop.** If your proxy does not
  strip client-supplied `X-Forwarded-For` headers, rate limiting can be evaded
  by spoofing it. Configure the proxy to overwrite, not append.
- **No WAF or DDoS protection.** Rate limiting is per-endpoint and
  application-level; volumetric attacks need to be handled at the network edge
  (Cloudflare, your load balancer, or similar).
- **No virus scanning on RFQ attachments.** They are stored and never re-served
  to a browser, but if anyone downloads and opens one locally, that is outside
  what this application can protect. Consider ClamAV if that matters to you.
- **Single-role model.** There is an `owner`/`editor` distinction in the schema,
  but the admin screens do not yet differentiate between them. Treat every
  admin account as fully privileged.
- **Outbound email is optional and unauthenticated at the DNS level.** If you
  configure `RESEND_API_KEY`, set up SPF, DKIM and DMARC for the sending domain
  or the notifications will land in spam — and your domain becomes easier to
  spoof.
- **Dependency updates are your responsibility.** Run `npm audit` regularly and
  keep Next.js current; a framework CVE bypasses everything described above.

## Verification

The security controls described here are exercised by a test suite that runs
against a live server rather than mocks — CSRF rejection, session revocation,
enumeration resistance, upload sniffing, path traversal, rate limiting, and the
full 2FA enrolment/challenge/recovery cycle. See `README.md` for how to run it.
